# CrunchGo 第二阶段：优化与高级功能

## 为什么 (Why)
第一阶段建立了核心的点餐流程。第二阶段旨在通过客户保留功能（会员/积分）、运营效率优化（每日取餐码、退款处理）和管理洞察（管理后台仪表盘）来完善业务闭环。

## 变更内容 (What Changes)
- **会员系统**: 实现支付时积分累积和积分历史记录。
- **订单优化**: 
    - 使用 Redis 实现每日滚动的取餐码（例如：A101）。
    - 实现已支付订单的退款逻辑（用户申请 -> 管理员批准 -> 微信退款）。
- **管理后台仪表盘**: 实现销售概览和热销商品的统计 API。
- **集成**: 完善微信支付签名验证（占位符）和打印机错误处理。

## 影响 (Impact)
- **受影响的规范**: 订单流程，用户资料。
- **受影响的代码**: 
    - `backend/app/models`: 添加 `UserPointLog`。
    - `backend/app/services`: 更新 `OrderService`，添加 `StatsService`。
    - `frontend-miniapp`: 显示积分历史，退款按钮。
    - `frontend-admin`: 仪表盘图表，退款审批 UI。

## 新增需求 (ADDED Requirements)

### 需求: 会员积分
- **累积**: 用户在支付成功后应根据订单金额获得积分（例如：1 元 = 1 积分）。
- **历史**: 系统应在 `UserPointLog` 表中记录每一笔积分交易（获取/消费/调整）。
- **显示**: 用户应能在小程序中查看积分余额和历史记录。

### 需求: 每日取餐码
- **格式**: 取餐码应为每日连续的序列号（例如：A001, A002），而不是随机字符串。
- **重置**: 序列号应在每天 00:00 重置为 1。
- **实现**: 使用 Redis `INCR` 操作，Key 类似于 `daily:seq:{date}`。

### 需求: 退款流程
- **申请**: 用户应能对已支付但未完成的订单申请退款。
- **批准**: 管理员应能查看退款申请并批准/拒绝。
- **执行**: 批准后的退款应触发（模拟）微信退款 API 并释放库存（如适用）。

### 需求: 管理统计
- **仪表盘**: 管理后台仪表盘应显示：
    - 今日总销售额 (GMV)。
    - 今日订单数。
    - 销量前 5 的商品。
